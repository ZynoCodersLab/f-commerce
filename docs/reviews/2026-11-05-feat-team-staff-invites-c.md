## Major

### 🟠 The new-account e2e arm cannot pass: the confirm-password field broke its selector and the Join button stays disabled, `frontend/e2e/team-invites.spec.ts:91`

**Problem**: The invite page renders two password inputs in `set-password` mode — `label="Password"` and `label="Confirm password"` (`frontend/src/app/invite/[token]/page.tsx:340, 360`, labels rendered as real `<label htmlFor>` elements by `frontend/src/components/ui/primitives.tsx:126`). The e2e fills the password with `invitePage.getByLabel(/password/i)` — `getByLabel` with a regex substring, case-insensitively matches the label text, so it resolves to **both** inputs and Playwright's strict mode aborts with an actionability error at line 91. The test then never fills `confirmPassword` at all: `page.tsx:384` disables submit unless `password.length >= 8 && password === confirmPassword`, so even a resolver that picked the first field would stall at the `.click()` on line 93 (`getByRole('button', { name: /^join /i })` auto-waits for enabled and times out). This arm (`test('invites, shows the one time link, and sends the invitee through it')`, line 49) is the **only** test that drives a brand-new user to `ACTIVE` through the page and asserts the dashboard opens; its earlier steps are all guards this failure hides.

**Why it matters**: `.github/workflows/ci.yml:97-98` runs `cd frontend && npx playwright test` after waiting for the worker, so once this branch is pushed the branch is red — `verify.md` item 21 (`npx playwright test` passes, including `e2e/team-invites.spec.ts`) cannot be ticked, and no run of that suite ever happened on this change (`gh run list` shows no run for `feat/team-staff-invites`; the confirm-password field is uncommitted work-in-tree from the last pass). The alternative failure is worse than a red bar: "fixing" it with `.first()` or `getByLabel('Password', { exact: true })` still leaves the Join button disabled, so the path most likely to be taken is weakening the assertion and losing the only end-to-end proof of the happy path the spec names in `index.md:291` (invite → link opens → `SENT` → name and password → `ACTIVE` → dashboard with that business) — the exact blind spot that earlier passes have been filling.

**Suggested fix**: Fill both fields by exact label (`getByLabel('Password', { exact: true })` and `getByLabel('Confirm password', { exact: true })`) so the submit button enables, keep the existing `waitForURL('**/dashboard')` assertion, and run the suite once with Redis up before pushing so the loop is actually proven rather than reasoned about. Nothing in the page needs to change — the page behaviour is correct and already covered by `page.test.tsx:212,236`.

## Minor

### 🟡 The invite page route never sends `Cache-Control: no-store`, `frontend/next.config.ts:129-133`

**Problem**: The spec's security model says "Invite token in the URL: set `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, and `X-Robots-Tag: noindex`" (`docs/specs/0009-team-staff-invites/index.md:270`). The `/invite/:path*` rule delivers exactly two of the three. The API side is complete — `setLinkHeaders` sets all three on both the success and the error branch (`backend/src/presentation/controllers/team.controller.ts:68-72`, called on both the success and the error branch of create `:196, 199`, resend `:213, 216`, preview `:295, 298`, and accept `:319, 326`) — which is what makes the omission on the page read as an oversight rather than a decision: `docs/specs/0009-team-staff-invites/verify.md:28` was quietly narrowed to "the `/invite/[token]` page sends `Referrer-Policy` and `X-Robots-Tag`", while line 270 of the spec it is supposed to verify was never reconciled. `frontend/next.config.test.ts:74-81` asserts the two headers it does send, so nothing fails when the third is absent.

**Why it matters**: Whether the HTML is actually cacheable depends on next's rendering-time behaviour for a dynamic segment with no `generateStaticParams` — an assumption the branch neither documents nor tests, and which changes with a Next upgrade or a `dynamic = 'force-static'` experiment. A shared cache or a prefetch storing the preview document means a stored copy of another person's invitation (business, inviter, email address) keyed by a URL whose path is a secret. It is one line to be explicitly correct on a control the spec calls out by name.

**Suggested fix**: Add `{ key: 'Cache-Control', value: 'no-store' }` to the `/invite/:path*` rule, extend the `next.config.test.ts` assertion to cover it, and either reconcile `verify.md:28` with `index.md:270` or record in the spec why the page deliberately downgrades it.

### 🟡 The worker's composition function is constructed inside the application layer, `backend/src/application/services/invite-worker.ts:119`

**Problem**: `processInviteEmailJob(deps, ...)` is exemplary — every dependency is injected through `InviteWorkerDeps`, which is why the unit tests can drive `SENT`/`SKIPPED`/`RETRY`/`FAILED` without a database. The file then undoes it one function later: `createInviteWorker()` constructs `DrizzleTeamRepository` and `DrizzleAuthRepository`, reaches for `config.APP_ORIGIN`, and binds `sendInviteEmail` from the infrastructure services, all from inside `application/`. That is the inner layer importing the outer, which AGENTS.md names explicitly ("Make outer layers depend on inner layers, never the reverse"), and it is the composition step the rest of the branch already puts in an outer file — `team.controller.ts:51-59` wires `TeamService` the same three dependencies, and `worker.ts` (the process entry point) is where the queue connection, database, and signal handling live. `invite-worker.ts:1-3` also drags in `bullmq`'s `Worker`/`Job` types for that reason.

**Why it matters**: This edge is what keeps the worker testable, and today the file stays honest only because tests import `processInviteEmailJob` rather than `createInviteWorker` — any future helper that reaches for `config` or a Drizzle repository at import time in this folder silently widens a dependency edge that no test can see. It also splits responsibility: a `Worker` factory, its event wiring, and a process-level composition root living two layers too deep.

**Suggested fix**: Move `createInviteWorker` next to `worker.ts` (or into `infrastructure/queue/`) and leave only `processInviteEmailJob` and `InviteWorkerDeps` in the application layer. `worker.ts` already imports both sides, so the call site changes by one import. Note that `auth.service.ts:5` and `business.service.ts:3` set the same precedent in this branch's neighbouring code, so this is an existing pattern being extended rather than a new break — it is worth fixing while the worker entry point is still new.

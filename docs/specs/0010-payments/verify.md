## API / runtime

- [x] `POST /api/orders` with valid `initialPayment` (including `CASH_ON_DELIVERY`, omitted `paymentDate`, explicit past `paymentDate`, and `referenceNumber` / `notes`) → returns 201 with `paidAmount`, `dueAmount`, `refundOwed: 0`, `paymentStatus`, and one entry in `payments` with `payment_date` defaulted to business today, `idempotency_key` null in DB, `ORDER_CREATED` audit metadata unchanged (`{ orderNumber, total }`), and one `PAYMENT_RECORDED` audit row → AC-1, AC-7, AC-14, AC-15
- [x] `POST /api/orders` with invalid `initialPayment`: amount above computed total, amount 0 or above 100,000,000, future `paymentDate`, impossible date `2026-02-30`, `BKASH` on a `USD` business, `referenceNumber` over 100 chars, `notes` over 500 chars, sent on a payload that would otherwise trigger a 24 hour duplicate → each returns 400 `VALIDATION_ERROR` with `initialPayment.<field>` in `fields` before duplicate detection (while `items.*` stays `items`), and writes nothing → AC-2, AC-13, AC-14
- [x] `POST /api/orders` duplicate flow and `Idempotency-Key` replay with `initialPayment` → 409 `DUPLICATE_ORDER` inserts no payment; resending with `confirmDuplicate: true` inserts the order and payment; replaying the order's `Idempotency-Key` with a different `initialPayment` returns 200 with the original stored order and payments and inserts nothing → AC-2
- [x] `POST /api/orders/:id/payments` on an active order (`PENDING` through `DELIVERED`) → returns 201 with full order detail, updates `paidAmount` and `dueAmount`, bumps `updatedAt`, keeps `version` unchanged, adds no status history row, and writes one `PAYMENT_RECORDED` audit row with entity type `PAYMENT` and actor name snapshot → AC-3, AC-7, AC-11, AC-15
- [x] `POST /api/orders/:id/payments` on `CANCELLED` and `RETURNED` orders, and with amount above `dueAmount` (including due 0) → returns 409 `ORDER_CLOSED` on closed orders and 409 `PAYMENT_EXCEEDS_DUE` with current `dueAmount` when over due, writing nothing → AC-4
- [x] Race two `POST /api/orders/:id/payments` requests that individually fit `dueAmount` but together exceed it → under the order row lock exactly one returns 201 and the other returns 409 `PAYMENT_EXCEEDS_DUE` with `paid_amount <= total` preserved → AC-4, AC-7
- [x] `POST /api/orders/:id/refunds` as `OWNER` on an active order and on a closed order, plus an amount above `paidAmount` → returns 201 with full order detail, lowers `paidAmount` (raising `dueAmount` on active or lowering `refundOwed` on closed), bumps `updatedAt` without changing `version`, writes `REFUND_RECORDED` audit; amount above `paidAmount` returns 409 `REFUND_EXCEEDS_PAID` with current `paidAmount` → AC-5, AC-7, AC-15
- [x] `POST /api/orders/:id/payments/:paymentId/void` as `OWNER` with valid reason, blank reason, already voided entry, malformed/unknown/cross order/cross tenant `paymentId`, and with an `Idempotency-Key` header → blank reason returns 400; valid returns 200 with void fields set once, recomputed totals, unchanged `version`, and `PAYMENT_VOIDED` audit (ignoring `Idempotency-Key`); repeat returns 409 `PAYMENT_ALREADY_VOIDED`; bad or foreign ids return 404 → AC-6, AC-12, AC-15, AC-16
- [x] `POST /api/orders/:id/payments/:paymentId/void` balance guards: (a) pay 1,000, refund 400, try to void the 1,000 payment; (b) pay 1,000, refund 400, edit total to 700, cancel order, then try to void the 400 refund → both return 409 `VOID_BREAKS_BALANCE` with current `paidAmount` and `total` (never 500) and leave the database unchanged → AC-6, AC-7
- [x] `POST /api/orders/:id/status` moving a partially paid order to `CANCELLED` or `RETURNED`, plus racing a concurrent payment against a cancel → locks the order row, sets `dueAmount` to 0, keeps `paidAmount` intact (`refundOwed` equals `paidAmount`, `paymentStatus` `REFUND_OWED`), runs existing stock movement, and returns full detail including `payments`; a racing payment either lands before cancel (leaving both reflected in `refundOwed`) or fails with 409 `ORDER_CLOSED` → AC-4, AC-7, AC-8
- [x] `PATCH /api/orders/:id` check order and locking: lower total below `paidAmount` (with matching and stale versions), edit a `PROCESSING` order, send a stale version with a valid total, send a valid total change, send a no op edit, and race an edit against a concurrent payment → `ORDER_LOCKED` runs before total checks, `TOTAL_BELOW_PAID` (with current `paidAmount`) runs before `ORDER_CHANGED`, `ORDER_CHANGED` runs before `CUSTOMER_ARCHIVED`, accepted edits recompute `dueAmount = newTotal - lockedPaid`, no op returns full detail with `payments`, and concurrent writes never store stale `dueAmount` → AC-7, AC-9
- [x] `GET /api/orders` with `paymentStatus` single and comma separated filters (`UNPAID`, `PARTIAL`, `PAID`, `REFUND_OWED`), combined with `status` and `q`, cursor replay with altered `paymentStatus`, and `paymentStatus=NONE` or unknown value → SQL `CASE` matches `derivePaymentStatus` across every order state (including total 0 active orders as `PAID` and closed paid 0 as `NONE`), rows include `paidAmount`, `paymentStatus`, and `refundOwed`, `NONE` and invalid values return 400 naming `paymentStatus`, and replaying a cursor on another `paymentStatus` set returns 400 naming `cursor` → AC-10
- [x] `GET /api/orders/:id` after recording payments, refunds, and voids and renaming the actor user → `payments` returns all entries (including voided) ordered by `paymentDate` then `createdAt` then `id` oldest first, and `recordedByName` / `voidedByName` retain the names captured when written → AC-11, AC-15
- [x] `Idempotency-Key` checks on `/payments` and `/refunds`: (a) empty or 101 char header → 400 naming `Idempotency-Key`; (b) used key sent to malformed/unknown/other business `:id` → 404 (never 409); (c) replay on same order and same kind with invalid body → 200 before body validation; (d) replay on another order → 409 `IDEMPOTENCY_KEY_CONFLICT`; (e) payment key replayed on `/refunds` for the same order → 409 `IDEMPOTENCY_KEY_CONFLICT`; (f) two concurrent requests with one key on same order → one 201 and one 200, single row; (g) two concurrent requests with one key on two different orders → one 201 and one 409 `IDEMPOTENCY_KEY_CONFLICT` → AC-12
- [x] `BKASH` and `NAGAD` on a `USD` business on create, `/payments`, and `/refunds` → 400 `VALIDATION_ERROR` naming `initialPayment.method` or `method`; switching a `BDT` business with existing bKash entries to `USD` keeps the old entries readable → AC-13
- [x] Past `paymentDate` before order creation (accepted) vs tomorrow in `businesses.timezone` (rejected 400 naming `paymentDate`) in a business on `Pacific/Kiritimati` or `America/New_York` when UTC is on a different day → server uses `todayInTimeZone(businesses.timezone)` → AC-14
- [x] Force an `audit_logs` insert failure during create with `initialPayment`, `/payments`, `/refunds`, and `/void` → transaction rolls back completely, returning 500 with no payment row, no void update, and no `paid_amount` / `due_amount` change → AC-15
- [x] Role and tenant matrix across every payment and business route: no token (401), bad token (401), missing business header (400), non member business (403), `STAFF` calling `/payments` and `GET /api/payments` (201 / 200), `STAFF` calling `/refunds` and `/void` (403 before reading or writing), cross tenant order or payment ids (404), and `GET /api/business/me` returning live `data.role` (`OWNER` or `STAFF`) matching the database after a role change → AC-16
- [x] `GET /api/payments`: omitted `from`/`to` defaults to month start through today in `businesses.timezone`; `from > to` returns 400 naming `from`, `to`; leap year `2024-01-01` to `2024-12-31` (366 inclusive days) returns 200 while `2024-01-01` to `2025-01-01` (367 inclusive days) returns 400 naming `from`, `to`; future `to` returns 200; response carries `items` (with `customerName`, `orderNumber`, `orderId`), `summary` (`collected`, `refunded`, `net`), and `nextCursor`; `kind=REFUND` sets `collected: 0` and negative `net`; voided rows appear in `items` but are excluded from `summary`; paging with `cursor` returns no duplicates and replaying a cursor with changed filters returns 400 naming `cursor` → AC-17
- [x] `GET /api/customers/:id/orders` after recording payments and cancelling an order → DTO shape is unchanged and customer `totalDue` equals the sum of active orders' updated `dueAmount` → AC-7, AC-10

## Acceptance criteria coverage

- AC-1 optional `initialPayment` on order create, `CASH_ON_DELIVERY` accepted, atomic transaction, null payment key, unchanged `ORDER_CREATED` metadata · covered by create UI steps and create API step
- AC-2 `initialPayment.<field>` validation before duplicate detection, duplicate 409 rollback, Create anyway, order replay · covered by create UI duplicate step and invalid/duplicate/replay API steps
- AC-3 `POST /api/orders/:id/payments` lock, totals, `updatedAt`, no version bump, audit, 201 full detail · covered by Record payment UI step and record payment API step
- AC-4 active status rule, `ORDER_CLOSED`, `PAYMENT_EXCEEDS_DUE` with `dueAmount`, concurrent payment lock · covered by two tab UI steps and closed/exceeds/race API steps
- AC-5 `POST /api/orders/:id/refunds` `OWNER` only, any status, `REFUND_EXCEEDS_PAID` with `paidAmount`, active vs closed effect · covered by refund UI steps and refund API step
- AC-6 void endpoint `OWNER` only, reason, once only, `PAYMENT_ALREADY_VOIDED`, `VOID_BREAKS_BALANCE` with `{ paidAmount, total }` in all statuses, 404 cases · covered by void UI steps and void API steps
- AC-7 `paidAmount` and `dueAmount` invariants, `0 <= paid <= total`, cached totals rewritten atomically, derived `refundOwed` and `paymentStatus` · covered by balance UI steps, all write API steps, and live schema check
- AC-8 cancel and return lock order row, zero `dueAmount`, preserve payments as `refundOwed`, run existing stock moves · covered by cancel UI step and status change API step
- AC-9 `PATCH /api/orders/:id` row lock, `ORDER_LOCKED` → resolve lines → `TOTAL_BELOW_PAID` → `ORDER_CHANGED` → `CUSTOMER_ARCHIVED`, no op full detail · covered by edit UI step and edit API step
- AC-10 derived `paymentStatus` on all order shapes, `GET /api/orders` `paymentStatus` filter rejecting `NONE`, cursor binding, unchanged customer orders DTO · covered by `/orders` and customer UI steps and list/customer API steps
- AC-11 `GET /api/orders/:id` `payments` array oldest first including voided, no status timeline rows · covered by detail UI step and detail API step
- AC-12 `Idempotency-Key` header validation, order 404 before lookup, same order+kind 200, cross order/kind 409, race handling, void ignores header · covered by idempotency and void API steps
- AC-13 eight methods, `BKASH`/`NAGAD` restricted to `BDT` on writes, historical labels preserved, all eight methods in `/payments` filter · covered by currency switch UI step and currency rule API step
- AC-14 integer amount bounds, `paymentDate` business today default, any past date allowed, future date rejected, reference and notes limits · covered by create UI steps and validation/timezone API steps
- AC-15 single transaction `audit_logs` rows for payment, refund, void, actor name snapshots, rollback on audit failure · covered by audit rollback and actor rename API steps
- AC-16 auth, tenant 404s, per route role middleware, `STAFF` vs `OWNER` matrix, live `role` on `GET /api/business/me` and `BusinessSettingsProvider` · covered by `STAFF` UI step and auth/role API step
- AC-17 `GET /api/payments` defaults, 366 inclusive day cap, future filter dates, `items`/`customerName`, `kind` filtered `summary`, voided excluded from summary, plain filter cursor · covered by `/payments` UI step and ledger API step
- AC-18 `/orders/new` Payment received section, Full amount, dynamic reference label, `CARD` warning, currency load sync, blank skips payment · covered by `/orders/new` UI steps
- AC-19 `/orders/[id]` Payments section, role gated buttons, prefilled dialogs, 409 close vs keep open behavior, edit error message, focus trap and WCAG AA · covered by `/orders/[id]` and keyboard UI steps
- AC-20 `/orders` payment status badge on desktop and mobile, payment filter chips combined with status and search, paging reset · covered by `/orders` UI step
- AC-21 `/payments` desktop sidebar and phone `More` nav, explicit month dates on every request, filters, summary, 20 per page Load more, states, WCAG AA · covered by `/payments` and keyboard UI steps
